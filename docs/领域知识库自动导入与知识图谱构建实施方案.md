# 领域知识库自动导入与知识图谱构建实施方案

> 文档状态：实施建议稿  
> 适用版本：Cognivia V6 质量稳定性迭代之后  
> 目标范围：领域知识库管理、自动知识图谱构建、诊断题生成、索引与领域发布  
> 明确边界：不修改学习者侧业务闭环，不修改 V6 Agent 契约和顶层学习工作流

## 1. 背景与目标

当前项目已经具备领域创建、文档上传、Markdown/PDF/TXT 解析、导入候选、候选校验、Candidate RAG 索引、检索冒烟、候选激活和领域 readiness 等基础能力。

现阶段的主要缺口不是“能否上传文档”，而是上传后仍需要管理员逐步审核、批准、构建索引、执行冒烟和发布；通用 Markdown 解析也不能自动理解结构化知识字段，自动生成的知识关系和诊断题不足以支撑可信知识图谱与领域就绪。

本方案目标是把管理员操作收敛为：

```text
创建领域
  -> 上传文件
  -> 系统自动解析、归纳学习方向、构图、出题、校验、建索引和冒烟
  -> 管理员查看学习方向建议、处理摘要和图谱预览
  -> 点击一次“确认并发布”
  -> 领域进入 ready
```

管理员不需要逐条编辑知识点、关系或题目。若系统无法自动得到可信结果，应整批停止并给出错误报告，不得静默发布低质量数据。

### 1.1 最终导入功能范围

最终导入功能包括：

- 支持结构化 Markdown、通用 Markdown、PDF 和 TXT；扫描 PDF 在未配置 OCR 时明确失败；
- 确定性解析结构化字段并生成稳定 Chunk，通用文档按功能开关启用模型抽取；
- 依据领域内 `external_id`、名称、内容和语义执行幂等新增、更新、合并或保守保留；
- 保存知识与多个来源 Chunk 的显式关联，支持来源补充和来源撤回；
- 根据显式关系、课程规则和有证据的模型判断生成候选知识关系；
- 从来源生成或导入单选题、简答题，并验证答案、解析、rubric、难度和题型分布；
- 自动执行来源、Schema、跨领域、前置环、路径覆盖、Candidate 索引和检索冒烟门禁；
- 通过持久化 ImportRun 展示进度、支持断点恢复、幂等重试和失败报告；
- 管理员查看摘要与图谱预览后一次确认发布，正式数据和活动索引指针事务切换；
- 已有领域支持 staged update、影响范围标记、来源撤回和旧版本继续服务。

## 2. 与学习业务流程的边界

本方案属于上游“领域内容生产与治理”，不改变下游学习业务流程。

### 2.1 领域知识库管理流程

```text
文档
  -> 内容块
  -> 知识点
  -> 知识关系
  -> 诊断题
  -> 自动校验
  -> 候选索引
  -> 发布领域包
```

### 2.2 学习者运行流程

```text
学习者选择 ready 领域
  -> 诊断
  -> 学情画像
  -> 知识检索
  -> 多 Agent 生成
  -> 双模型审核
  -> 学习反馈
  -> 辅导与决策
  -> 画像和学习路径更新
```

两条流程只通过已发布领域数据连接。候选知识、候选关系和候选索引不会被学习者运行时读取。

### 2.3 不得修改的内容

本方案不修改：

- `backend/app/agents/contracts.py`
- `backend/app/agents/state.py`
- `backend/app/agents/contract_adapters.py`
- `backend/tests/contracts/`
- `docs/agent-contract-v6.md`
- `docs/contracts/v6/`
- `build_learning_graph()` 顶层结构
- 反馈证据进入画像的现有治理规则

知识导入是独立后台业务流水线，不新增一套学习 Agent 图，也不把导入任务塞入冻结的 LangGraph State。

## 3. 核心设计原则

1. 文档是知识来源，Chunk 是证据单元，知识点是诊断、检索和画像的业务单元。
2. 采用“局部抽取、全局归一、候选配对、关系校验”，不让模型对整份文档一次生成整张图。
3. MySQL 保存业务主数据，ChromaDB 保存语义索引，不引入 Neo4j。
4. 模型生成的数据先进入候选区，最终一次“确认并发布”视为对整批候选的管理员确认。
5. 关系必须有证据。文档顺序只能作为弱信号，不能把相邻条目直接串成前置链。
6. 不以模型自报置信度作为唯一依据，必须结合结构、来源、规则、语义和图约束。
7. 低置信度关系自动过滤，不要求管理员逐条处理。
8. Candidate 索引构建失败时继续使用旧活动索引。
9. 发布优先将正式数据与活动索引指针放在同一个 MySQL 事务中切换；兼容期使用持久化阶段和恢复协议保证最终一致性。
10. 普通日志只记录 ID、状态、计数、耗时和错误摘要，不记录完整正文、完整题目或完整生成内容。

## 5. 业务状态机

### 5.1 领域状态

继续使用：

```text
draft -> preparing -> ready -> disabled
```

- `draft`：只有领域基本信息。
- `preparing`：正在自动导入、构图、出题、校验或构建索引。
- `ready`：诊断、检索和生成均通过门禁。
- `disabled`：禁止创建新任务，历史任务和资源继续可查看。

### 5.2 导入运行状态

`KnowledgeDocument` 表示上传文档及其来源生命周期，`KnowledgeImportRun` 表示一次可重试、可恢复的处理运行。一个文档在输入版本或配置变化后可以产生新的 ImportRun，不能把长流水线的全部恢复信息只压在文档状态字段中。

目标状态机：

```text
queued
  -> parsing
  -> extracting
  -> normalizing
  -> graph_generating
  -> question_generating
  -> validating
  -> index_pending
  -> indexing
  -> smoke_testing
  -> ready_to_publish
  -> publishing
  -> ready
```

异常状态：

```text
failed
needs_attention
deleted
```

- `failed`：基础设施、模型、解析或索引任务失败，可自动重试。
- `needs_attention`：自动处理完成但质量门禁无法满足，不允许发布。
- `deleted`：管理员删除且相关候选、暂存数据和候选索引已清理。

自动修复最多执行两轮。两轮后仍无法满足门禁时进入 `needs_attention`，不得无限循环。

## 6. 数据模型方案

### 6.1 复用现有表

继续复用：

- `domains`
- `knowledge_documents`
- `knowledge_import_candidates`
- `knowledge_items`
- `knowledge_relations`
- `diagnostic_questions`
- `index_build_jobs`
- 学习路径、资源和评测相关现有表

### 6.2 增加稳定证据 Chunk 与来源关联

建议新增 `knowledge_chunks`，保存文档解析后的稳定证据单元，而不是只在进程内生成临时 section。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 内部主键 |
| `public_id` | VARCHAR(64) | 稳定 Chunk ID |
| `document_id` | BIGINT | 来源文档 |
| `domain_code` | VARCHAR(64) | 领域隔离 |
| `chunk_index` | INT | 文档内顺序 |
| `heading_path_json` | JSON | Markdown 标题路径或 PDF 页标题 |
| `page_start` | INT NULL | PDF 起始页 |
| `page_end` | INT NULL | PDF 结束页 |
| `content` | TEXT | 原始证据内容 |
| `checksum` | VARCHAR(64) | 内容 SHA-256 |
| `previous_chunk_id` | BIGINT NULL | 上一内容块 |
| `next_chunk_id` | BIGINT NULL | 下一内容块 |
| `created_at` | DATETIME | 创建时间 |

同时新增轻量 `knowledge_item_sources`，解决一个知识点由多个文档共同支持时的来源、更新和删除语义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 内部主键 |
| `knowledge_item_id` | BIGINT | 正式或 staged 知识点 |
| `chunk_id` | BIGINT | 来源 Chunk |
| `document_id` | BIGINT | 来源文档，便于按文档撤回 |
| `source_quote_hash` | VARCHAR(64) | 被采用原文摘录的 SHA-256 |
| `is_primary` | BOOLEAN | 是否为主要来源 |
| `created_at` | DATETIME | 创建时间 |

唯一约束为 `(knowledge_item_id, chunk_id)`。`source_locator_json` 继续保存便于 API 返回的来源摘要，但不再承担唯一的数据关联职责。

已经被正式知识引用的 Chunk 不物理删除。管理员删除文档时默认执行“撤回来源”：删除该文档对应的来源关联并重新计算知识有效性；只有知识点失去全部有效来源时，才将其置为 `needs_attention` 或进入待下线变更，不得直接删除其他文档共同支持的正式知识点。

### 6.3 扩展知识关系证据

现有 `knowledge_relations` 只有端点和关系类型，无法证明自动构图的可信性。建议增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `confidence` | DECIMAL(4,3) | 综合置信度，不是单纯模型自评分 |
| `evidence_json` | JSON | Chunk ID、原文摘录 hash、规则依据和理由 |
| `generation_method` | VARCHAR(64) | `explicit/structure/rule/model/hybrid` |
| `source_document_id` | BIGINT NULL | 主要来源文档 |

关系候选继续保存在 `knowledge_import_candidates.payload_json` 中；只有最终确认发布后才写入正式关系表。

### 6.4 保持诊断题兼容

P0 继续保留 `diagnostic_questions.knowledge_item_id` 作为主要考查知识点，避免修改现有画像和评分链。

候选题可以在 `payload_json` 中保存：

```json
{
  "knowledge_candidate_id": "kic_xxx",
  "secondary_knowledge_candidate_ids": [],
  "question_type": "single_choice",
  "stem": "...",
  "answer": 1,
  "explanation": "...",
  "source_chunk_ids": ["kchunk_xxx"]
}
```

若后续证明综合题的多知识点权重对掌握度计算有显著收益，再以向后兼容方式增加 `question_knowledge_links`；本次不修改现有主关联语义。

### 6.5 外部知识 ID

结构化文件中的 `knowledge_id` 作为领域内稳定外部 ID 使用。建议为 `knowledge_items` 增加可空的 `external_id VARCHAR(128)`，并建立唯一约束 `(domain_code, external_id)`：

1. `public_id` 始终由系统生成，是内部稳定 ID，不接受外部文件直接赋值。
2. `external_id` 保存原始 `knowledge_id`，用于同领域幂等查找。
3. 同一领域再次导入相同 `external_id` 且内容相同时执行 `skip`，只补充缺失来源。
4. 同一领域再次导入相同 `external_id` 且内容变化时生成 staged update，不直接覆盖正式知识。
5. 相同 `external_id` 出现相互矛盾的内容时进入 `needs_attention`，不得静默选择任一版本。
6. 缺少 `external_id` 时，才回退到规范化名称、内容 checksum、来源位置和语义复核。

### 6.6 增加可恢复导入运行与活动索引指针

新增 `knowledge_import_runs`，保存一次导入的持久化执行状态：

| 字段 | 类型 | 说明 |
|---|---|---|
| `public_id` | VARCHAR(64) | 导入运行 ID，也是 SSE 关联 ID |
| `document_id` | BIGINT | 输入文档 |
| `domain_code` | VARCHAR(64) | 领域隔离 |
| `current_step` | VARCHAR(64) | 当前步骤 |
| `status` | VARCHAR(32) | queued/running/interrupted/failed/needs_attention/ready_to_publish/publishing/ready |
| `input_version` | VARCHAR(64) | 文档、配置和 Prompt 组合版本 |
| `artifact_manifest_json` | JSON | 各步骤输出 ID、版本和 hash |
| `step_state_json` | JSON | 步骤状态、attempt、耗时和错误摘要 |
| `lease_owner` | VARCHAR(64) NULL | 当前执行者 |
| `lease_expires_at` | DATETIME NULL | 超时接管时间 |
| `started_at/finished_at` | DATETIME NULL | 运行时间 |

活动索引指针必须进入 MySQL 管理，可新增 `domain_index_manifests`，至少保存 `domain_code`、`active_collection`、`index_version`、`source_data_version`、`embedding_model`、`status` 和时间戳。Chroma collection 只保存不可变向量数据，不再承担活动版本指针的事务语义。

## 7. 文档解析与知识抽取

### 7.1 解析策略

继续支持 PDF、Markdown 和 TXT：

- PDF 保存页码；扫描件没有 OCR 时明确失败。
- Markdown 保存标题层级、列表、代码块和结构化字段。
- TXT 保存段落编号和相邻关系。
- 文件按 SHA-256 去重。
- 单个 Chunk 建议 300～600 中文字，相邻内容可保留约 80 字上下文，但证据定位必须指向不重叠的稳定原文单元。

### 7.2 结构化 Markdown 优先

对以下格式采用确定性字段解析，不调用模型猜测：

```markdown
## 1. 梯度下降基础
- **knowledge_id:** `ml_优化算法与理论_003`
- **category:** 基础优化
- **difficulty:** 1
- **tags:** gradient-descent, optimization, learning-rate
- **source:** [来源标题](https://example.com)
- **license:** CC BY-SA 4.0

知识正文……
```

映射规则：

| Markdown 字段 | 候选字段 |
|---|---|
| 二级标题 | `name` |
| `knowledge_id` | `external_knowledge_id` |
| `category` | `category` |
| `difficulty` | `difficulty` |
| `tags` | `tags` |
| `source` 标题 | `source_title` |
| `source` URL | `source_url` |
| `license` | `license_note` |
| 元数据后的正文 | `content` |

必须满足：

- 文档总标题和“共 N 条”说明不得生成知识点；
- 精确生成 114 条，而不是 115 条；
- 不把元数据文本混入知识正文；
- 不使用固定难度和固定标签覆盖原始字段；
- 不因相邻章节自动生成前置关系。

### 7.3 通用文档回退

没有结构化字段时：

1. 先按标题和段落生成 Chunk。
2. 每个 Chunk 独立抽取知识候选和局部关系候选。
3. 模型只能依据输入 Chunk，不允许补充外部事实。
4. 输出必须通过 Pydantic Schema。
5. 每个候选必须保存可在 Chunk 中定位的 `source_quote`。

### 7.4 能力权重与证据能力

结构化文档未提供能力权重时，由确定性规则根据内容类型设置默认值，再由自动校验归一化：

- 理论定义、原理说明：提高 `theory` 和 `knowledge_breadth`。
- 操作步骤、代码实现、环境配置：提高 `practice`。
- 案例、调试、故障排查：提高 `problem_solving`。
- `learning_speed` 权重固定为 0。

证据能力只允许：

```text
definition, example, operation, code, troubleshooting
```

不得为了满足诊断题分布而把纯理论知识伪装成 `operation`。

## 8. 知识点归一化与去重

### 8.1 去重顺序

```text
同领域稳定外部 ID
  -> 规范化名称
  -> 内容 checksum
  -> 来源位置
  -> Embedding 候选召回
  -> 模型语义复核
```

### 8.2 自动决策

- 外部 ID 相同、内容相同：`skip`。
- 外部 ID 相同、内容变化：`update`，标记 `needs_reembedding=true`。
- 名称和内容 hash 相同：`merge`。
- 高语义相似但存在概念差异：保留独立节点。
- 无法确定是否同义：不得静默合并；优先保留独立节点，并在质量报告中记录警告。

Embedding 相似度阈值必须通过本项目固定样本标定，不能直接照搬外部方案中的 0.80 或 0.92。

## 9. 自动知识关系生成

### 9.1 关系类型

P0 继续使用现有四种：

| 关系 | 语义 |
|---|---|
| `prerequisite` | source 是 target 的前置知识 |
| `depends_on` | source 的理解或实现依赖 target |
| `related_to` | 概念相关但无明确学习方向 |
| `next_step` | source 完成后的推荐下一学习节点 |

不新增 Neo4j 风格的 `PARENT_OF/PART_OF/SIMILAR_TO`。层级信息先保存在分类和标题路径中；同义概念在归一化阶段合并。

### 9.2 候选知识点对召回

禁止对全部知识点做平方级两两模型判断。每个知识点仅召回有限候选对：

1. 同一标题路径或同一分类；
2. 相邻章节窗口内的知识点；
3. 标签有交集；
4. 内容或名称 Embedding Top-K；
5. 正文显式提及对方名称或别名；
6. 被同一道诊断题共同引用。

实现采用分层召回：结构化 `prerequisites` 和原文显式依赖表达进入事实关系候选；其余节点按
分类、标签、难度、教学角色与 Embedding 构建浅层分支式 `next_step` 推荐骨架。事实候选按无序
端点去重，模型只判断带精确证据片段的局部候选，不再为每个节点固定生成双向候选对。

### 9.3 关系证据优先级

从高到低：

1. 文本显式表达，如“在学习 A 之前需要掌握 B”。
2. 结构化文件显式 `prerequisites` 或关系字段。
3. 标题层级与确定性课程规则。
4. 同一 Chunk 中的概念依赖描述。
5. 题目解析中的明确先后步骤。
6. 标签、相似度和文档顺序等弱信号。

共同出现在一道题中最多证明 `related_to`，不能单独证明 `prerequisite`。

### 9.4 综合置信度

综合置信度由程序计算，至少考虑：

- 是否有原文证据；
- 证据是否能在 Chunk 中定位；
- 结构规则是否支持；
- 语义召回得分；
- 关系方向是否符合难度和章节逻辑；
- 主判定与独立校验是否一致；
- 图约束是否通过。

模型自报置信度只作为一个输入，不直接决定发布。

“独立校验”必须满足：

- 生成和校验使用不同 system prompt 与结构化输出 Schema；
- 条件允许时使用不同模型通道，至少不能把同一次生成结果中的自评分视为独立校验；
- 校验模型只能依据来源 Chunk，不允许引入外部常识补证；
- 引用定位、端点、重复边、环和领域隔离由确定性程序校验；
- 主判定与独立校验冲突时重新取证一次，仍冲突则过滤该关系，不为满足数量或覆盖率强行保留。

建议策略：

```text
综合置信度 >= 0.85：进入待发布图谱
0.70～0.85：自动二次校验
二次校验仍不确定：过滤
< 0.70：过滤
```

阈值必须通过本项目关系金标准样本校准。

### 9.5 图结构校验与自动修复

必须检查：

- 端点存在且同领域；
- 无自环；
- 无重复边；
- `prerequisite` 无环；
- 关系方向合法；
- 关系证据完整；
- 孤立节点比例；
- 每个学习方向是否形成可用子图；
- 各学习方向有效路径覆盖率是否达到发布门槛。

检测到前置环时：

1. 找出环内置信度最低的边；
2. 重新检索证据并复核；
3. 无法证明时移除该边；
4. 最多修复两轮；
5. 仍有环则整批进入 `needs_attention`。

## 10. 自动诊断题生成

### 10.1 生成原则

- 题目由已确认知识候选和来源 Chunk 生成。
- 答案、解析和评分规则必须能从来源推出。
- 每题绑定一个主要知识点。
- 不把模型常识当成文档事实。
- 题目生成结果继续经过独立验证。

### 10.2 数量与分布

生成数量由领域 readiness policy 决定。第二领域最低 10 道，完整比赛领域建议至少 60 道。

必须满足当前运行时最低分布：

| 题型 | 理论知识 | 实操知识 |
|---|---:|---:|
| 单选题 | >=3 | >=3 |
| 简答题 | >=2 | >=2 |

同时覆盖主要分类和难度层级。若来源中缺少实操证据，不得伪造实操题，应将导入标记为 `needs_attention` 并说明领域资料不足。

### 10.3 题目校验

- 题干、答案、解析和来源完整；
- 选择题答案属于选项；
- 干扰项不产生第二个正确答案；
- 简答题 rubric 可执行；
- 答案能被来源 Chunk 支持；
- 重复或高度相似题自动替换；
- 题目难度与知识点难度不明显冲突。

题目生成和题目验证必须使用不同 Prompt；条件允许时使用不同模型通道。结构、选项、答案索引、rubric 和来源定位由程序验证，事实与答案支持度由验证模型仅根据来源 Chunk 判断。同一模型在同一次输出中的自评分不构成独立验证。

## 11. 自动处理编排

### 11.1 新增编排服务

建议增加 `knowledge_import_orchestrator.py`，只负责任务状态和步骤编排，不混入具体解析、抽取或索引逻辑。

职责拆分：

| 服务 | 职责 |
|---|---|
| `knowledge_document_service.py` | 上传、文件存储和任务入口 |
| `knowledge_parser_service.py` | 文件解析和稳定 Chunk |
| `knowledge_extraction_service.py` | 知识候选抽取 |
| `knowledge_normalization_service.py` | 规范化、去重和幂等决策 |
| `knowledge_graph_generation_service.py` | 候选对召回和关系生成 |
| `diagnostic_generation_service.py` | 诊断题生成和分布补齐 |
| `knowledge_import_validation_service.py` | Schema、来源、题目和图门禁 |
| `knowledge_import_publish_service.py` | 暂存、候选索引、冒烟和发布 |
| `knowledge_import_orchestrator.py` | 状态机、重试和步骤编排 |

### 11.2 持久化执行与恢复协议

编排器必须以 `knowledge_import_runs` 为事实来源，不能只依赖 FastAPI 进程内 BackgroundTasks。每个步骤使用 `(run_id, step, input_version)` 作为幂等键，并在提交步骤结果时同时保存 artifact ID、版本和 hash。

恢复规则：

1. Worker 执行前获取有过期时间的 lease，同一导入同一时刻只能有一个执行者。
2. 服务启动时查找 `running` 且 lease 已过期的运行，标记为 `interrupted` 后从最后一个已提交步骤恢复。
3. 已存在相同 artifact hash 的模型或 Embedding 结果直接复用，不重复计费和写入。
4. 自动恢复最多两轮；两轮后仍失败进入 `needs_attention`。
5. 管理员重试默认从失败步骤继续；只有输入文档、领域配置或 Prompt 版本变化时才创建新 `input_version` 并使后续步骤失效。
6. SSE 事件包含单调递增的 `event_id`、`run_id`、`step`、`attempt`、状态、计数和错误摘要，客户端通过 Last-Event-ID 断线续传。

### 11.3 自动执行步骤

上传成功后后台自动执行：

```text
parse
  -> extract
  -> normalize
  -> generate_graph
  -> generate_questions
  -> validate
  -> stage
  -> build_candidate_index
  -> smoke_test
  -> projected_domain_readiness
```

全部通过后进入 `ready_to_publish`。管理员不需要点击“批准”“构建索引”“冒烟测试”等中间按钮。

### 11.4 模型调用治理

- 使用 OpenAI-compatible API。
- 每类任务使用独立 system prompt 和结构化输出 Schema。
- 重试最多 3 次，等待 1s、3s、5s。
- 保存模型名、Prompt 版本、输入 Chunk ID、输出 hash、耗时和 Token 统计。
- 使用 `knowledge_import_batches` 按输入哈希保存批次 artifact；每批完成立即提交，重启只恢复失败
  或未完成批次。单批按 8K Token 动态组包，生成、复核和全局并发分别限制为 3、2、4。
- 400 输入超限立即拆批；429、5xx 和网络超时按 1s、3s、5s 重试；单批失败不回滚其他批次。
- 普通日志不保存完整 Chunk、完整题目或完整关系解释。
- 导入模型调用不复用或修改学习 Agent 的 V6 State。
- 通用文档模型抽取由功能开关控制；模型不可用时，结构化 Markdown 的确定性解析、既有知识管理和旧活动索引仍可使用。

## 12. 发布与一致性

### 12.1 发布前投影检查

在 `ready_to_publish` 前，应使用“当前 published 数据 + 本次 staged 数据”计算预期 readiness。只有预计发布后可以通过门禁，才向管理员展示“确认并发布”。

### 12.2 一次确认发布

推荐将活动索引指针保存在 MySQL。Chroma Candidate collection 在发布前完成构建和冒烟，发布时只切换数据库中的活动版本指针。管理员点击后：

1. 锁定领域和导入任务；
2. 校验本次 Candidate manifest、输入版本和冒烟版本未变化；
3. 在同一个 MySQL 事务中将 staged 知识、来源关联、关系和题目切换为 published；
4. 在同一事务中更新 `domain_index_manifests.active_collection` 和 `index_version`；
5. 在同一事务中执行最终 readiness、更新领域状态并保存发布审计摘要；
6. 提交后异步清理过期 collection，清理失败不回滚已经成功的发布。

运行时始终从 MySQL 读取活动 collection。这样正式业务数据与活动索引指针在同一个数据库事务内切换，Chroma 只提供预先构建的不可变 collection。

若首期暂时保留文件 manifest，则本能力只能称为“可恢复的协调式发布”，必须额外持久化 `prepared -> manifest_switched -> db_committed -> verified` 阶段、旧 manifest 和恢复动作，并在服务启动时执行 reconciliation；不得宣称跨 MySQL 和文件系统具有原生原子事务。

管理员的这次整体确认同时构成模型建议关系进入正式图谱前的管理员确认，符合“模型建议不得未经确认直接写入正式图谱”的治理要求。

### 12.3 更新已有领域

新文档导入已有领域时：

- 活动索引在 Candidate 构建完成前保持不变；
- 变更知识设置 `needs_reembedding=true`；
- 使用正式知识关系计算影响范围；
- 受影响学习路径设置 `needs_refresh=true`；
- 来源或审核规则变化时将相关资源标记为 `review_stale`；
- 已开始的历史任务和资源不被改写；
- 新任务读取新发布的活动索引。
- 相同知识点增加或撤回来源时通过 `knowledge_item_sources` 计算有效来源，不按单个 `source_document_id` 直接删除正式知识。

## 13. 领域发布门禁

在现有 readiness 基础上增加知识图谱质量检查。

| 检查项 | 门槛 |
|---|---:|
| 已发布知识点 | 主领域 >=50；第二领域 >=10 |
| 有效诊断题 | 主领域 >=60；第二领域 >=10 |
| 学习方向 | >=1 |
| 缺失能力权重 | 0 |
| 缺失来源 | 0 |
| 无效或跨领域关系 | 0 |
| 前置关系环 | 0 |
| 正式关系证据完整率 | 100% |
| 学习方向有效路径覆盖率 | >=80% |
| 无来源知识节点 | 0 |
| Candidate RAG ready | 必须通过 |
| 名称和释义检索冒烟 | 必须通过 |
| 跨领域检索污染 | 0 |
| 画像运行时 | ready |
| 诊断运行时 | ready |
| 生成运行时 | ready |

全节点路径参与率定义：能够进入至少一条合法 `prerequisite/depends_on/next_step` 学习路径的知识点数，除以预计发布后的全部有效知识点数。分母不得缩小为已经参与关系的节点。根节点允许没有前置边但必须具有可达后继，叶节点允许没有后继但必须能够从前置节点到达。

除全节点参与率不低于 80% 外，孤立节点率不得高于 15%；每个学习方向的路径参与率不得低于 80%，且节点数不少于 4 的方向必须至少存在一条包含 4 个节点的合法主路径。前置环、自环、重复边、无证据方向性关系和未解决复核冲突均阻止发布。

`related_to` 只用于检索扩展和知识浏览，不计入路径参与率、孤立节点或主路径计算。关系总数只作为异常监控指标，不设置硬性数量门槛，避免为了数量生成噪声边；对于 100～150 个节点，约 100～200 条可信方向性关系可作为人工观察区间，但不能替代准确率和路径可用性门禁。

关系 precision 和方向准确率属于系统版本的离线质量基线，不是单次未知领域可以直接计算的 readiness 指标。发布具备模型增强能力的系统版本前，必须在固定金标准上达到：关系 precision `>=90%`、关系方向准确率 `>=90%`，并在报告中记录样本版本、分子、分母和失败样本 ID。单次领域导入只使用来源完整性、独立验证结果、未解决冲突、图约束和路径可用性等可观测门禁。

## 16. 失败、重试与回滚

### 16.1 可自动重试

- 模型调用超时或瞬时失败；
- Embedding 服务瞬时失败；
- Candidate 索引构建中断；
- 冒烟测试的可恢复基础设施错误。

重试必须从最后一个已提交步骤恢复，并复用相同 `input_version` 下已验证的 artifact。不得通过重复点击产生并行运行或重复候选。

### 16.2 不自动降级发布

- 来源无法定位；
- 前置图仍有环；
- 学习方向有效路径覆盖率或关系准确率不足；
- 诊断题分布不满足；
- 跨领域关系或检索污染；
- Candidate manifest 与冒烟版本不一致；
- 有 unresolved 关系被错误纳入正式图谱。

### 16.3 回滚原则

- 解析失败不创建正式知识；
- 校验失败不构建活动索引；
- Candidate 构建失败不影响旧索引；
- 冒烟失败不能发布；
- MySQL 活动索引指针方案中，事务提交前失败直接回滚，事务提交后旧 collection 清理失败只记录待清理任务；
- 文件 manifest 兼容方案中，发布失败按持久化发布阶段执行 reconciliation，恢复旧 manifest 和数据库状态；
- 删除未发布导入任务时清理候选、暂存数据和候选 collection；
- 撤回已发布文档时删除该文档的来源关联并重新计算知识有效性，不直接删除其他来源共同支持的知识、关系和题目。

## 17. 测试方案

### 17.1 单元测试

1. 结构化 Markdown 精确解析字段。
2. 文档总标题不生成多余知识点。
3. 114 条输入得到 114 条知识候选。
4. 外部 ID 幂等导入。
5. 难度、标签和逐条来源不被固定默认值覆盖。
6. Chunk ID 稳定且来源摘录可定位。
7. 同义候选归一化和非同义相似概念不误合并。
8. 候选对数量受 Top-K 限制，不执行全量平方配对。
9. 自环、重复边、跨领域边和前置环被拒绝。
10. 无证据前置关系被过滤。
11. 诊断题选项、答案、解析和来源校验。
12. 理论/实操题型分布满足门禁。
13. 多文档共同支持同一知识点时来源关联正确，撤回单个文档不误删知识。
14. 相同 `(run_id, step, input_version)` 重复执行不产生重复候选或重复模型调用记录。
15. `related_to` 不计入学习路径覆盖率。

### 17.2 集成测试

1. 上传后自动运行到 `ready_to_publish`。
2. 中间候选对学习者不可见。
3. 自动生成知识、关系和题目均落在正确领域。
4. Candidate 索引失败时旧索引仍可检索。
5. 冒烟能检索本次导入知识且无跨领域结果。
6. 一次确认后正式数据和 MySQL 活动索引指针在同一事务中生效。
7. readiness 失败时领域不能设置为 ready。
8. 删除或重试不会产生重复知识和重复关系。
9. 已有领域更新会标记路径刷新和资源审核过期。
10. Worker 重启后可从最后一个已提交步骤恢复。
11. 并发重试只能有一个运行获得 lease。
12. 发布事务提交前失败时旧数据和旧索引继续生效。
13. 发布提交后清理旧 collection 失败不影响新版本可用性。
14. 文件 manifest 兼容模式覆盖 manifest 切换前、切换后和 DB 提交后的崩溃恢复。

### 17.3 端到端验收

固定演示案例：

```text
管理员创建 ai_ml_basics
  -> 上传结构化 Markdown
  -> 系统自动处理
  -> 摘要显示知识、关系、题目、图谱和索引全部通过
  -> 管理员点击确认发布
  -> 学习者选择 ai_ml_basics
  -> 完成诊断
  -> 生成画像和学习路径
  -> 生成三类资源
  -> 双模型审核通过
  -> 反馈触发辅导或调整
```

验收要求：全程不修改代码、Prompt 或数据库，不逐条编辑候选，不出现 `ai_app_dev` 的知识、题目、来源或检索结果。

## 20. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 模型生成错误前置关系 | 原文证据、独立校验、无环检查、低置信度过滤 |
| 相似概念被错误合并 | 外部 ID 优先、保守合并、固定反例评测 |
| 自动出题存在错误答案 | 来源约束、结构校验、独立题目验证 |
| 一键发布形成半发布状态 | Chroma collection 不可变，正式数据和 MySQL 活动索引指针在同一事务切换，并执行崩溃点测试 |
| Worker 重启造成任务悬挂或重复执行 | 持久化 ImportRun、步骤幂等、lease、启动恢复和 artifact 复用 |
| 多文档合并后删除一个来源误删知识 | 显式 `knowledge_item_sources`、来源撤回和失源待下线流程 |
| `related_to` 噪声边制造虚假高覆盖 | 路径覆盖只统计方向性学习关系，并用金标准校验 precision 和方向 |
| 新领域污染主领域 | domain_code 全链路校验和跨领域检索冒烟 |
| 自动化流程耗时过长 | 有限候选对、批量模型调用、步骤结果复用 |
| 日志泄露完整知识内容 | 普通日志只保存 ID、hash、状态、计数和摘要 |
| 改造影响学习 Agent | 导入服务独立，冻结 V6 文件和契约测试 |

## 21. 完成定义

本方案完成需要同时满足：

1. 管理员只填写领域代码和名称后上传一个结构化 Markdown，不手工配置学习方向。
2. 结构化输入条目数准确率为 100%，114 条输入精确得到 114 条知识候选。
3. 外部 ID 幂等、多来源合并和来源撤回测试全部通过。
4. 所有正式知识、关系和诊断题来源定位有效率为 100%。
5. 固定金标准上的关系 precision 和方向准确率均不低于 90%。
6. 前置关系无环、无跨领域边，全节点及各学习方向路径参与率均不低于 80%，孤立节点率不高于 15%，每个不少于 4 个节点的方向至少有一条 4 节点主路径。
7. 诊断题结构有效率和来源支持率均为 100%，数量与理论/实操分布满足 readiness policy。
8. 系统自动构建 Candidate 索引并完成名称、释义和领域隔离冒烟。
9. 系统自动建议学习方向；管理员不逐条编辑，只需查看摘要并点击一次确认发布。
10. ImportRun 重启恢复、重复执行幂等、并发 lease 和发布崩溃点测试全部通过。
11. 发布失败或旧 collection 清理失败时，已有领域和旧活动索引不受破坏。
12. 新领域进入 ready 后可以复用现有诊断、画像、检索、生成、审核、反馈和路径流程。
13. `ai_app_dev` 主领域及 V6 契约测试无回归。
14. 第二领域完整流程可以通过自动化测试和比赛演示复现。

## 22. 最终结论

本项目不需要复制题目驱动平台的“从题目抽标签并同步 Neo4j”实现。应借鉴其“题目关联知识点、作答更新掌握度”思路，同时发挥 Cognivia 已有文档、候选、RAG、审核和领域治理能力，建立：

```text
文档有来源
+ Chunk 有定位
+ 来源可合并和撤回
+ 知识点可归一
+ 关系有证据
+ 题目可测量
+ 图谱可校验
+ 任务可恢复
+ 数据与索引指针事务切换
+ 发布只需一次确认
```

第一阶段优先交付不依赖模型可用性的结构化文档可靠导入，通用文档的模型抽取、自动构图和自动出题作为受功能开关控制的增强能力。该能力是领域知识库管理的上游增强，不改变学习者侧的多 Agent 个性化学习闭环。
