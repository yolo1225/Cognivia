## 1. 实施目标和首要结论

### 1.1 本轮优化要解决什么

本方案只围绕当前项目的真实实现问题：

1. 前端实际使用的流式导学绕过 Tutoring Agent，反馈闭环在主入口中没有真实执行；
2. Feedback 中的结构化证据没有装配到画像分析输入，画像更新长期固定为 `no_change`；
3. 简答题只是关键词包含计数，不符合“AI 辅助评分并给出评语”的 P0 需求；
4. Agent Message 接收方和审核仲裁 SSE 条件存在失真，前端展示不能完全代表真实执行；
5. 正式演示环境存在评测画像覆盖入口，普通学习目标有机会影响真实画像选择；
6. 学习路径只有推荐顺序，没有节点完成、验证、解锁和推进状态；
7. Agent Contract 的 V5/V6 事实来源以及生产 Prompt 来源不统一；
8. 文档上传目前只是实验能力，不能形成可用知识体系；
9. 诊断、画像、导学和前端仍存在 `ai_app_dev` 硬编码；
10. 管理员还不能完整完成“导入—复核—索引—发布”；
11. 生成与双审核真实运行明显慢于内部目标，需要在质量不回退的前提下提速；
12. 当前迁移能力只有部分底层基础，尚未通过第二领域证明。

审查问题覆盖索引：

| 审查项 | 方案位置 | 优先级 |
|---|---|---|
| 流式导学绕过 Tutoring Agent | 7.1～7.3 | P0-1 |
| 反馈证据无法进入画像更新 | 7.4～7.10 | P0-1 |
| 领域硬编码和假迁移风险 | 第 4～6 章 | P0-3～P0-5 |
| 简答题不是 AI 辅助评分 | 7.11 | P0-2 |
| 生成、审核和导学过慢 | 第 8 章 | P1 |
| Agent Message 与仲裁 SSE 失真 | 7.13 | P1 |
| 正式演示可触发评测画像覆盖 | 3.3、7.14 | P0-0 |
| Prompt 与合同版本治理混乱 | 3.3、7.15 | P0-0/P1 |
| 学习路径没有真实推进 | 7.12 | P0-2 |
| 管理员知识导入和无代码迁移 | 第 4～6 章 | P0-3～P0-5 |

### 1.2 首先优化什么

**第一个必须处理的是当前演示入口的真实性断链**：修复流式导学、反馈证据装配和后续任务创建，并关闭正式演示中的评测画像覆盖。原因是这些问题会让用户看到“导学和动态更新”的界面，却没有真正进入 `interpret_feedback -> analyze_profile -> ...` 主图。

完成这组 P0 热修后，**领域建设的第一个功能优化才是知识导入**。

原因：

- 新领域运行依赖知识点、关系、题目、难度和能力权重；
- 当前上传把整份文档做成一个知识点，后续诊断和画像无法使用；
- 如果先做领域切换页面，只会得到“能切换界面、不能完成业务”的假迁移；
- 主领域新增知识也需要同一条真实导入链路。

因此实际执行顺序是：

```text
冻结现有主领域基线
  -> 修复流式导学、反馈证据、评测隔离和 SSE 真实性
  -> 补齐简答题 AI 评分和学习路径推进
  -> 完成真实知识导入
  -> 移除领域硬编码
  -> 完成管理员领域发布与学习者选择
  -> 优化生成审核速度
  -> 完成评测和第二领域证明
```

本文件原有阶段编号按主题保留，避免已有评审引用失效；开发排期必须以下一节的“实际执行顺序”为准，不得按章节编号机械执行。

### 1.3 最终用户体验

管理员：

```text
创建领域
  -> 上传专业文档
  -> 查看知识点、关系和题目候选
  -> 修改或批准
  -> 构建 Candidate 索引
  -> 查看冒烟结果
  -> 发布
```

学习者：

```text
选择领域
  -> 诊断
  -> 画像和学习路径
  -> 检索
  -> 三类个性化资源
  -> 双模型审核
  -> 导学反馈
  -> 有证据时更新画像和局部资源
```

新增领域不修改 Python、TypeScript、Prompt、Agent 合同或 LangGraph。

## 2. 总体优化顺序

| 顺序 | 优先级 | 阶段 | 核心产物 | 前置依赖 |
|---:|---|---|---|---|
| 0 | P0 | 冻结主领域基线和安全开关 | 可重复回归的主流程、演示环境无画像覆盖 | 无 |
| 1 | P0 | 阶段 4A：流式导学和反馈证据 | 前端主入口真实进入 Tutoring Agent 和统一学习图 | 阶段 0 |
| 2 | P0 | 阶段 4B：简答题评分和路径推进 | AI 辅助评分、可验证节点状态机 | 阶段 4A |
| 3 | P0 | 阶段 1：真实知识导入 | 结构化候选、复核、Candidate 索引和发布 | 阶段 0 |
| 4 | P0 | 阶段 2：领域去硬编码 | 所有节点统一使用任务 `domain_code` | 阶段 1 |
| 5 | P0 | 阶段 3：管理员领域闭环 | 创建、准备、校验、发布、选择领域 | 阶段 2 |
| 6 | P1 | 阶段 4C：可观测性和契约治理 | 消息、SSE、Prompt 与合同事实来源一致 | 阶段 4A |
| 7 | P1 | 阶段 5：生成审核提速 | 一次检索、并行生成、批审核、局部复审 | 阶段 0 |
| 8 | P1 | 阶段 6：评测和迁移证明 | 50 例主评测、小规模第二领域 | 阶段 1～5 |

执行规则：

- P0 阶段没有通过完成定义，不进入依赖它的下一阶段；
- 每个阶段先补后端真实能力，再接前端状态；
- 每次改造都回归 `ai_app_dev` 主流程；
- fixture 只用于测试，不进入演示和正式指标；
- 不修改冻结的 V5 Agent 合同和顶层图。
- 每一项问题必须同时具备“代码改造、测试、可观测证据和完成标准”，仅修改页面文案不算完成。

## 3. 阶段 0：冻结主领域基线

### 3.1 目标

在开始领域和导入改造前，先证明当前主领域的可见流程仍然可用，避免后续无法判断回归来自哪里。

### 3.2 具体工作

1. 固定一个演示学习者和一个完整首次生成案例。
2. 固定一条反馈案例：
   - 首次“太难”只解释、不改画像；
   - 内容错误进入资源复核、不改画像。
3. 固定当前 Candidate manifest、embedding 模型和主领域种子版本。
4. 记录当前后端健康检查和前端可访问路由。
5. 运行现有单元测试、合同测试和主流程验收。
6. 记录三类资源是否生成、来源是否展示、双审核是否有两条真实调用记录。
7. 固化当前正式 50 案例性能基线：端到端 P50 `87.6s`、P95 `206.8s`，生成节点 P50 `59s`、审核节点 P50 `21s`、导学分类 P50 `23s`。
8. 固化反馈链路基线：统计 `profile_update_required=true/false`、真实反馈任务数、仲裁 SSE 数和路径节点完成数；当前全为 0 的项必须保留为改造前证据。

### 3.3 立即执行的安全开关和治理决议

代码大改前先完成两项不依赖业务重构的止损动作：

1. 正式演示和普通 live 环境强制 `enable_evaluation_overrides=false`，健康检查必须显示该值；
2. 指定 Agent Contract 维护者对 V5/V6 冲突作一次性决议：要么生产运行回到冻结 V5，要么正式批准 V6，并同步更新 AGENTS.md、合同文档、Schema、样例和测试名称。

决议完成前：

- 普通实现人员不得修改 `contracts.py`、`state.py`、`contract_adapters.py` 或合同测试；
- 不得新增 V4/V5/V6 混用；
- 当前业务修复只能使用已存在的合同字段做装配；
- 正式演示不得接受学习目标中的 `[[evaluation_case:...]]` 标记。

### 3.4 不做的事

- 不重构冻结合同；
- 不先增加新领域页面；
- 不先替换数据库或 Agent 框架；
- 不以 fixture 成功代替真实链路。

### 3.5 完成标准

- 主领域诊断、画像、路径、三类资源和反馈页面均可访问；
- Candidate RAG ready；
- 三类资源都有来源；
- 主副审核为两个独立模型通道；
- 现有核心测试通过；
- 正式演示健康检查中 `evaluation_overrides_enabled=false`；
- V5/V6 只能存在一个被书面确认的生产事实来源；
- 形成一份可重复执行的基线检查清单。

## 4. 阶段 1：把实验上传改成真实知识导入

### 4.1 当前问题

`backend/app/services/knowledge_document_service.py` 当前：

- 一整份文档只创建一个 KnowledgeItem；
- 分类固定为“上传文档”；
- 难度固定为 2；
- 不提取知识关系；
- 不生成诊断题；
- 不生成画像能力权重；
- 解析后仍回到语义不清的排队状态；
- 数据可能先进入知识表，管理员没有候选复核。

这条链路是当前最优先的真实能力缺口。

### 4.2 目标流程

```text
上传文件
  -> 文件校验与文本解析
  -> 章节感知分段
  -> 抽取知识点候选
  -> 生成关系候选
  -> 生成诊断题候选
  -> 程序校验和去重
  -> 管理员复核
  -> 批准候选写入正式数据
  -> Candidate 索引
  -> 检索冒烟
  -> 发布
```

### 4.3 第一步：调整数据模型

#### KnowledgeItem

在现有模型上增加：

```text
ability_weights_json
source_locator_json
status
```

保留并真正使用：

```text
difficulty
evidence_capabilities_json
source_document_id
needs_reembedding
```

约束：

- 难度为 1～5；
- 前四项能力权重非负且总和为 1；
- 学习速度权重固定为 0；
- 来源能定位到页码、章节或段落；
- 正式检索只读取 `published` 知识。

#### Domain

增加可直接查询的 `status`：

```text
draft -> preparing -> ready -> disabled
```

`config_json` 只保存展示或非关键扩展数据，不保存 Prompt、Agent 路由和核心审核门槛。

#### 导入候选

增加一个轻量候选表 `knowledge_import_candidates`，避免为知识、关系和题目分别扩张表：

```text
public_id
document_id
domain_code
candidate_type
payload_json
source_locator_json
confidence
status
validation_errors_json
```

`candidate_type`：

```text
knowledge_item
knowledge_relation
diagnostic_question
```

`status`：

```text
pending -> approved / rejected / needs_edit
```

所有模型和表变更通过 Alembic 迁移完成。

### 4.4 第二步：拆分导入服务

不要继续让 `knowledge_document_service.py` 同时负责存储、解析、知识创建和索引。

建议职责：

| 模块 | 职责 |
|---|---|
| `knowledge_document_service.py` | 上传、文件状态和后台任务入口 |
| `knowledge_parser_service.py` | PDF/MD/TXT 确定性文本解析 |
| `knowledge_extraction_service.py` | 知识点、关系、题目候选抽取 |
| `knowledge_import_validation_service.py` | Schema、来源、关系、题目和重复校验 |
| `knowledge_import_publish_service.py` | 批准候选写入正式表 |
| 现有 Candidate Index | embedding、manifest、冒烟和发布 |

命名可以按现有项目规范调整，但职责不能重新混回一个大函数。

### 4.5 第三步：确定性解析

P0 支持 PDF、Markdown、TXT：

- 校验类型、大小、文件签名和 SHA-256；
- PDF 保存页码；
- Markdown 保存标题层级；
- TXT 保存段落编号；
- 保留列表、代码块和操作步骤边界；
- 扫描 PDF 没有 OCR 时明确失败；
- 日志不保存完整正文。

输出统一结构：

```json
{
  "document_id": "kdoc_xxx",
  "sections": [
    {
      "heading_path": ["章节", "小节"],
      "page_start": 3,
      "page_end": 4,
      "text": "...",
      "checksum": "..."
    }
  ]
}
```

### 4.6 第四步：候选抽取

模型只从输入章节抽取，不允许补充外部事实。

知识候选：

```text
name, category, content, difficulty, tags
ability_weights, evidence_capabilities
source_locator, source_quote, confidence
```

关系候选：

```text
source_candidate_id, target_candidate_id
relation_type, reason, source_locator, confidence
```

题目候选：

```text
knowledge_candidate_id, question_type, stem
options, answer, rubric, explanation
difficulty, source_locator, confidence
```

自动生成结果全部进入候选表，不直接写正式知识和题库。

### 4.7 第五步：程序校验和去重

知识候选：

- 名称、正文、分类、难度、来源完整；
- source quote 能在解析文本中找到；
- 能力权重合法；
- 证据能力属于允许集合；
- 同领域 ID 唯一。

关系候选：

- 两端存在且同领域；
- 禁止自环、重复和跨领域；
- `prerequisite` 图无环。

题目候选：

- 题干、答案、解析完整；
- 选择题答案属于选项；
- 答案能由来源推出；
- 难度为 1～5；
- 关联知识存在；
- 重复题相似度低于门槛。

去重顺序：

```text
稳定外部 ID
  -> 规范化名称
  -> 内容 hash
  -> 语义相似度
  -> 来源位置
```

冲突必须标记为 `skip`、`create`、`merge`、`update` 或 `manual_review`，不得静默覆盖。

### 4.8 第六步：管理员复核

`frontend/src/pages/DomainHubPage.vue` 增加或整合：

- 来源文档；
- 导入任务；
- 知识候选；
- 关系候选/图谱；
- 题目候选；
- 索引与发布。

管理员可：

- 对照原文修改候选；
- 合并重复知识；
- 调整难度和能力权重；
- 编辑或拒绝关系；
- 预览题目、答案和解析；
- 批量批准高置信度候选；
- 查看阻断错误。

### 4.9 第七步：Candidate 索引和发布

```text
批准候选
  -> 事务写入 KnowledgeItem、Relation、Question
  -> needs_reembedding=true
  -> 复用未变化向量
  -> 构建新 Candidate collection
  -> 校验 manifest 与 metadata
  -> 名称查询和释义查询冒烟
  -> 管理员发布
  -> 原子切换活动 manifest
```

不能边解析边写活动集合。Candidate 构建失败时，当前活动索引继续可用。

### 4.10 API

在现有文档接口基础上补充：

```text
GET   /api/v1/knowledge/imports/{import_id}
GET   /api/v1/knowledge/imports/{import_id}/candidates
PATCH /api/v1/knowledge/imports/{import_id}/candidates/{candidate_id}
POST  /api/v1/knowledge/imports/{import_id}/validate
POST  /api/v1/knowledge/imports/{import_id}/approve
POST  /api/v1/knowledge/imports/{import_id}/build-index
POST  /api/v1/knowledge/imports/{import_id}/smoke-test
POST  /api/v1/knowledge/imports/{import_id}/publish
GET   /api/v1/knowledge/imports/{import_id}/events
```

响应继续使用 `schema_version`、`request_id`、`data/error`，进度用 SSE。

### 4.11 测试

必须新增：

1. 多章节文档生成多个候选；
2. 每个候选有来源；
3. 同文件重试不重复；
4. 扫描 PDF 不生成空知识；
5. 自环和前置环阻止批准；
6. 错误题目答案阻止批准；
7. 未批准候选不进入检索；
8. Candidate 失败不影响活动索引；
9. 冒烟失败不能发布；
10. 发布后新知识可检索且无跨领域污染。

### 4.12 完成标准

- 文档不再直接创建单个临时知识项；
- 管理员能复核知识、关系和题目候选；
- 正式知识具备难度、能力权重和来源定位；

## 7. 阶段 4：修复真实闭环、评分、路径与运行治理

### 7.1 当前问题

本阶段不是新增页面，而是把现有页面背后的真实执行补齐。已经确认的断点如下：

| 问题 | 当前实现证据 | 影响 |
|---|---|---|
| 流式导学绕过 Tutoring Agent | `backend/app/api/v1/tutoring.py` 的 `/messages/stream` 直接调用 `gateway.stream_text()`，完成事件固定 `task_id=None` | 前端主入口没有反馈分类、画像判断和后续任务 |
| 后续反馈任务被禁用 | `backend/app/services/tutoring_service.py` 使用 `if False` 包住 `create_feedback_task()` | 即使 Agent 建议生成或复核，也不会进入统一学习图 |
| 反馈证据未进入 State | `backend/app/workers/generation_worker.py` 构造 `FeedbackContext` 时未读取 `profile_change_evidence_json` | 已确认测验或行为证据在 Worker 处丢失 |
| 画像评估输入为空 | 正常节点调用 `build_analyze_profile_input()` 时没有显式传 `knowledge_assessments` | 画像分析长期只能 `no_change` |
| 简答题为关键词计数 | `backend/app/services/profile_service.py::score_answer()` 仅统计 rubric 字符串是否出现在答案中 | 不满足 AI 辅助评分，易被关键词堆砌绕过 |
| Agent Message 接收方失真 | `generation_worker.py::_message()` 把 receiver 统一写为 `orchestrator_agent` | 消息表不能证明真实节点交接 |
| 仲裁 SSE 条件不匹配 | `generation_tasks.py` 读取 `arbitration_required`，运行摘要实际保存 `arbitration` 数组 | 审核分歧事件基本不触发 |
| 评测画像可被用户文本触发 | `evaluation_case_service.py` 从学习目标解析 `[[evaluation_case:...]]` | 正式演示存在画像被覆盖风险 |
| 学习路径固定首节点 | `generation_worker.py::_learning_path_snapshot()` 固定 `nodes[0]` 为当前节点 | 路径只是推荐列表，不会真实推进 |
| 合同和 Prompt 来源不一致 | 规范冻结 V5，生产和测试出现 V6，合同测试文件仍名为 V4；Markdown Prompt 未被生产加载 | 后续开发容易继续产生假版本和过期规则 |

当前数据库抽查中，画像分析节点已完成 `417` 次，`profile_update_required=true` 为 `0` 次、`false` 为 `417` 次。这不是“所有学习者都刚好不需要更新”的合理业务结果，而是必须用真实集成案例纠正的断链基线。

### 7.2 第一步：统一流式和非流式入口

目标模块：

- `backend/app/api/v1/tutoring.py`；
- `backend/app/services/tutoring_service.py`；
- `backend/app/services/tutoring_api_service.py`；
- `backend/app/services/resource_tutoring_service.py`；
- `backend/app/agents/tutoring_agent.py`；
- `frontend/src/api/tutoring.ts`。

抽出唯一业务函数，例如：

```text
execute_tutoring_turn()
  -> 加载 resource、task、learner、domain
  -> 保存 learner message
  -> 执行 TutoringAgent
  -> 保存 Agent Run 和 Agent Message
  -> 保存 Feedback 意图和安全摘要
  -> 创建可能的验证问题
  -> 按证据和 Agent 决策创建可选 feedback generation task
  -> 保存 reply、feedback、run、message 和 task
  -> 返回 TutoringTurnResult
```

- `/messages` 和 `/messages/stream` 都只能调用该函数，禁止任一路由直接调用 `gateway.stream_text()` 形成旁路；
- 非流式接口直接返回 `TutoringTurnResult`；
- 流式接口先发送 `accepted/agent_status`；优先由 Tutoring Agent 的同一次模型调用产生 reply delta，并在结尾校验完整结构化结果。若当前供应商不能稳定流式解析结构化输出，MVP 可在单次完整调用后对真实 Agent 回复分块，不得为了“真流式”再发第二次模型请求；
- 删除 `tutoring_service.py` 中禁用任务创建的 `if False`：`incorrect/error_mark_text + review` 可直接创建资源复核任务且不更新画像；`challenge/regenerate` 等画像驱动任务必须同时满足 confirmed assessment、`needs_generation` 和动作白名单；
- `completed` 事件必须返回真实 `feedback_id`、`feedback_intent`、`profile_update_required`、`recommended_action`、`decision_reason` 和可空但真实的 `task_id`；
- 后台 Worker 只能在事务提交后启动，创建失败时返回明确错误，不能给前端假 `task_id`；
- SSE 只是同一业务结果的传输方式，不能形成第二套分类、存储或任务创建逻辑。

### 7.3 第二步：反馈分类

| 反馈 | 即时动作 | 画像 |
|---|---|---|
| `too_hard` | 追问、解释、必要时给验证题 | 无证据不变 |
| `too_easy` | 给应用/迁移验证题 | 无证据不变 |
| `confusing` | 换讲法、补例子 | 不变 |
| `incorrect` | 重新检索并复核资源 | 不变 |
| `helpful` | 记录适配成功 | 通常不变 |
| 低评分 | 追问或复核 | 不单独更新 |

Feedback 继续保存：

```text
feedback_intent
recommended_action
profile_update_required
profile_change_evidence_json
decision_confidence
affected_knowledge_ids_json
decision_reason
```

模型可以识别意图，但不能自行制造画像证据。

### 7.4 第三步：验证题和 AnswerRecord

MVP 优先复用当前领域已批准的 DiagnosticQuestion：

```text
Tutoring Agent 判断需要验证
  -> 按 knowledge_id、difficulty、question_type 选一题
  -> 保存题目消息和 pending 状态
  -> 学习者回答
  -> 服务端评分
  -> 写入 AnswerRecord
  -> 形成结构化证据
```

这样不需要先引入另一套动态题目表，也能保证答案和来源已审核。

如果当前知识点没有合适题目：

- 返回“题库暂不足以验证”；
- 画像保持不变；
- 可将生成新验证题作为未来能力；
- 不能让 LLM 临时出题后直接修改画像。

AnswerRecord 的 `answer_summary_json` 增加安全的证据元数据：

```json
{
  "evidence_type": "tutoring_validation",
  "difficulty": 3,
  "confidence": 0.9,
  "confirmed": true,
  "feedback_id": 123,
  "tutoring_session_id": 456,
  "consumed_by_profile_id": null
}
```

不记录完整敏感答案。

### 7.5 第四步：证据装配

反馈 generation task 启动前读取：

- 当前 learner profile；
- 本 tutoring session；
- Feedback；
- 关联 AnswerRecord；
- 当前 resource 和 learning package；
- 当前任务 domain。

映射到冻结合同允许的：

- `FeedbackContext.supporting_evidence`：把 `profile_change_evidence_json` 中合法且同领域的证据转换为 `EvidenceRef`；
- `AnalyzeProfileInput.knowledge_assessments`：把已评分 AnswerRecord/Assessment 转为 `KnowledgeAssessment`。

具体装配位置在 Worker 或节点服务层：

1. `generation_worker.py::_initial_state()` 读取 Feedback、关联 AnswerRecord 和 Assessment；
2. 为每条证据生成稳定 `evidence_id`，同时校验 learner、domain、knowledge、feedback 和 session 归属；
3. 调用 `build_analyze_profile_input(state, knowledge_assessments=...)` 时显式传入评估列表；
4. `contract_adapters.py` 属于冻结文件，不得通过修改默认值解决调用方漏传；
5. 没有 confirmed AnswerRecord 时数组为空，Profile Agent 必须输出 `no_change`；
6. `profile_update_required=true` 后在同一事务中标记证据已消费，任务重试按 evidence ID 幂等。

### 7.6 第五步：画像更新算法

#### P0 先做确定性证据门禁

向上调整满足之一：

- 同知识点至少 3 道有效题，目标难度不低于当前资源，综合分 `>=0.80`，置信度 `>=0.75`；
- 两次独立验证均 `>=0.75`，且至少一次为应用、迁移或实操。

向下调整必须同时满足：

- 两次已评分失败；
- 已给一次补救解释；
- 第二次仍低于 `0.40`；
- 题目难度没有超出画像合理范围；
- 排除题目、资源和环境错误；
- 置信度 `>=0.75`。

单次“太难”“太简单”、星级、点赞、自述和资源错误权重均为 0。

#### P1 再升级 Beta 掌握度

```text
mastery_k = alpha_k / (alpha_k + beta_k)

alpha_new = alpha_old + weight * score
beta_new  = beta_old + weight * (1 - score)

weight = reliability * confidence
       * difficulty_factor * recency_factor
```

初始使用弱先验 `alpha=2, beta=2`。

建议证据权重：

| 证据 | 权重 |
|---|---:|
| 快捷标签、评分、自述、资源错误 | 0 |
| 单道导学验证题 | 0.5 |
| 多题分阶测试 | 1.0 |
| 初始诊断 | 1.0 |
| 已验证实操任务 | 1.2 |

### 7.7 第六步：迟滞和画像版本

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| 未掌握 | `<0.35` | `>=0.45` |
| 易混淆 | `0.35～0.55` | 超出缓冲区 |
| 部分掌握 | `0.55～0.78` | 超出缓冲区 |
| 已掌握 | `>=0.82` | `<0.72` |

只有同时满足才创建画像新版本：

1. mastery 变化超过 `0.10` 或跨过迟滞边界；
2. 能力维度变化 `>=5` 或薄弱知识列表有效改变；
3. 有 confirmed 证据；
4. 综合置信度 `>=0.75`；
5. 证据与画像同领域；
6. 证据未被消费。

否则记录证据并返回 `no_change`。

### 7.8 第七步：局部刷新

画像有效变化后：

1. 计算受影响知识点；
2. 沿关系找到受影响路径节点；
3. 找到引用这些知识的资源；
4. 只为受影响资源创建 revision plan；
5. 回到共享检索、生成和审核节点；
6. 未受影响资源继续复用；
7. 新包通过后原子替换当前包。

### 7.9 测试

1. 首次“太难”只解释；
2. “太简单”无答题证据时 `no_change`；
3. 有效高分证据提高掌握度；
4. 一次失败不降低画像；
5. 两次失败但资源错误时不降低；
6. 内容错误进入资源复核；
7. 重复 AnswerRecord 不重复消费；
8. 其他领域证据被拒绝；
9. 流式和非流式产生相同业务记录；
10. 画像未变化时不生成画像驱动的新学习包。

### 7.10 反馈链完成标准

- 所有自然语言反馈进入真实 Tutoring Agent；
- 验证题有正式 Question 和 AnswerRecord；
- 画像变化有可追踪证据；
- 无证据反馈稳定返回 `no_change`；
- 资源错误不会降低画像；
- 只刷新受影响路径和资源；
- `/messages` 与 `/messages/stream` 产生相同 Feedback、Run、Message、证据和任务记录；
- 至少一个真实集成案例产生 `profile_update_required=true`，并能追踪到 AnswerRecord 和画像新版本。

### 7.11 简答题改为真实 AI 辅助评分

目标文件：

- `backend/app/services/profile_service.py`；
- `backend/app/services/diagnostic_service.py`；
- `backend/app/models/diagnostic.py`；
- 诊断提交接口和对应前端类型。

当前 `score_answer()` 的 rubric 字符串包含计数只能作为预检，不能继续作为简答题最终分数。P0 使用以下流水线：

```text
答案格式和空值检查
  -> 确定性 rubric 命中预检
  -> LLM 对照题干、结构化 rubric、标准来源和学习者答案独立评分
  -> 分项得分、命中点、缺失点、错误点、总分、置信度和评语
  -> 程序一致性门禁
  -> AnswerRecord
```

实现规则：

1. 选择题继续使用确定性评分，不调用模型；
2. 简答题必须至少发生一次真实模型调用，模型输出使用独立内部 Pydantic Schema，不修改 Agent 冻结合同；
3. rubric 改为分项结构，每项包含 `criterion_id`、`description`、`max_score`、`required_concepts` 和允许的等价表达；
4. 模型必须给出每项得分、简短依据、缺失点、事实错误和一条面向学习者的中文评语；
5. 关键词预检只做异常检测。预检与模型总分差异大于 `0.20`，或两者通过/不通过冲突时，取保守分并标记 `scoring_uncertain=true`，不得自动给高分；
6. 防关键词堆砌：没有解释概念关系、因果或操作目的时，即使命中关键词也不能获得完整分；
7. 同一诊断会话的少量简答题可在一个受控批次中评分，减少模型往返；批次输出失败时只重试失败题，不重评已成功题；
8. 模型不可用时将 session 置为 `scoring_failed` 或 `pending_scoring` 并允许重试，不能静默回退为关键词最终分；
9. `AnswerRecord` 保存 `score`、`is_correct`、`ai_comment` 和安全评分摘要：评分方法、模型名、rubric 版本、分项分数、置信度和不确定标记；完整答案只存在受控业务字段，不进入普通日志。

测试：

- 同义正确答案不会因缺少字面关键词被判 0 分；
- 只堆砌关键词但没有正确解释的答案不能通过；
- 事实错误会在分项结果和评语中出现；
- 预检与模型严重分歧时执行保守策略；
- 模型失败不会生成“已评分”画像证据；
- 简答题结果可被转换为后续 `KnowledgeAssessment`。

完成标准：诊断结果页能展示真实 AI 评语和分项依据，数据库存在实际模型调用记录，画像使用的是最终受控分数而不是关键词计数。

### 7.12 把学习路径改为可推进的轻量状态机

MVP 不新增复杂路径事件表，优先扩展 `learning_paths.path_json`：

```json
{
  "stages": [
    {
      "name": "RAG 检索基础",
      "knowledge_ids": ["kid-rag-retrieval"]
    }
  ],
  "current_node_id": "path-node-003",
  "node_states": {
    "path-node-003": {
      "path_node_id": "path-node-003",
      "knowledge_id": "kid-rag-retrieval",
      "status": "current",
      "completed_at": null,
      "completion_evidence_ids": [],
      "completion_condition": {
        "type": "graded_quiz_score",
        "threshold": 0.8
      }
    }
  }
}
```

保留现有 `stages/knowledge_ids` 作为路径结构，`node_states` 只叠加运行状态，避免为了推进功能重写整条路径格式。旧路径首次读取时由确定性兼容逻辑生成 node state，不调用模型。

节点状态只允许：

```text
locked -> current -> completed
locked/current -> skipped（仅管理员或明确业务规则）
```

新增服务和 API：

```text
POST /api/v1/learning-paths/{path_id}/nodes/{node_id}/verify
POST /api/v1/learning-paths/{path_id}/nodes/{node_id}/complete
```

实现规则：

1. `verify` 读取 completion condition 对应的 AnswerRecord、分阶测试或已验证实操证据，返回是否满足及原因；
2. `complete` 必须引用已通过验证的结构化证据，禁止前端只传 `completed=true`；
3. 节点完成后，在同一事务中写入 `completed_at/evidence_ids`，将下一个所有前置已完成的节点改为 `current`；
4. 前置未完成的节点保持 `locked`，图中可以有多个可并行 `current` 节点，但必须明确一个 `current_node_id` 作为默认推荐；
5. `generation_worker.py::_learning_path_snapshot()` 从 `current_node_id` 或节点状态读取当前节点，不再固定使用 `nodes[0]`；
6. 画像有效变化或知识更新引发局部刷新时，按稳定 `knowledge_id` 继承未受影响节点的完成状态，新增节点重新计算锁定状态，删除节点保留在历史路径版本中；
7. 节点验证结果同时可作为画像证据，但必须继续经过 7.6～7.7 的证据门禁，不能因“完成按钮”直接更新画像。

测试：

- 未达到阈值不能完成节点；
- 合法测试证据完成当前节点并解锁后继；
- 缺少前置时后继保持 locked；
- 重复 complete 幂等；
- 跨 learner、domain、path 的证据被拒绝；
- 路径局部刷新保留未受影响完成状态；
- Worker 读取的 current node 与报告页一致。

完成标准：至少一个演示学习者能够完成节点、失败后补救、再次验证并推进到下一节点，报告页和生成任务都读取同一个当前节点。

### 7.13 修复 Agent Message 和审核仲裁 SSE

准确架构口径固定为：

- LangGraph State/节点输出是 Agent 之间的真实数据传递机制；
- `AgentMessageRecord` 是对真实节点交接的标准化审计投影，不宣称为独立点对点消息总线；
- SSE 是任务、Run、审核和路径状态的传输层，不生成业务事实。

后端改造：

1. 将 `generation_worker.py::_message()` 改为显式接收 `receiver`；
2. 按真实下一节点记录 `orchestrator -> tutoring/profile`、`tutoring -> profile`、`profile -> retrieval/finalize`、`retrieval -> generation`、`generation -> review`、`review -> finalize` 和修订回路；
3. 每条投影包含 `task_id/session_id`、sender、receiver、message type、节点名、合同版本、输入/输出摘要和时间；
4. 不在消息表保存完整画像、完整回答或完整资源；
5. `backend/app/api/v1/generation_tasks.py` 不再检查不存在的 `output.arbitration_required`，应读取审核摘要中的 `arbitration` 数组，并在任一 `item.required=true` 时发送仲裁事件；
6. SSE 事件携带真实 `task_id/resource_id/review_report_id`，并能反查数据库记录；
7. 前端把“Agent 消息”说明为“结构化交接记录”，避免将审计投影误称为网络消息总线。

测试：

- 首次生成和反馈分支的 sender/receiver 与 LangGraph 拓扑一致；
- 修订回路的消息方向正确；
- 构造主副审核分歧后必定收到 `arbitration_started/arbitration_completed`；
- 无分歧时不发送仲裁事件；
- SSE 中的 task、resource 和 report 均可查到；
- 前端固定计时器或硬编码步骤不会覆盖后端状态。

完成标准：用一个固定分歧案例可以从 LangGraph Run、Message 投影、ReviewReport 和 SSE 四处得到相互一致的证据。

### 7.14 隔离评测画像覆盖

正式方案不允许从普通 `learning_goal` 解析评测 case 并覆盖真实学习者画像。建议直接移除 live Worker 对 `evaluation_profile_override(learning_goal)` 的调用：

```text
test_script 读取 evaluation case
  -> 在隔离评测命名空间创建测试 learner/profile
  -> 用真实 profile_id 创建 generation task
  -> provider_mode=evaluation
  -> 运行同一生产图
  -> 评测结束后按脚本规则清理或保留审计结果
```

环境规则：

1. demo/live/production 固定 `enable_evaluation_overrides=false`；
2. evaluation runner 使用服务端受控的 case ID，不接受浏览器传入的画像快照；
3. 普通用户输入中的 `[[evaluation_case:...]]` 作为保留标记拒绝或转义，不参与任何画像选择；
4. `/api/v1/health/dependencies` 明确返回 `evaluation_overrides_enabled` 和当前 provider mode；
5. evaluation 仍使用真实模型、真实 Candidate RAG、真实双审核和相同质量门禁，只隔离测试身份和输入数据。

测试：

- 普通 learner 在学习目标中构造 marker，使用的仍是其数据库画像；
- demo/live 健康检查始终为 false；
- evaluation runner 的 case 画像与普通学习者数据隔离；
- 评测模式不会把测试画像写成普通学习者最新画像；
- 关闭开关后 50 案例仍能通过专用 runner 复现。

完成标准：正式演示不存在任何由用户文本触发的画像覆盖路径，评测脚本仍能使用真实生产图复现指标。

### 7.15 统一 Agent Contract 和生产 Prompt 事实来源

当前规范把 V5 定义为冻结事实来源，但生产 Worker 和合同测试出现 `agent-contract-v6`，测试文件仍命名为 `test_agent_contract_v4.py`。这不是普通 Agent 实现者可以自行修复的代码细节，而是合同维护者的阻断项。

合同维护者必须二选一：

1. 回到 V5：生产常量、Worker、测试断言和运行记录全部改回 V5；或
2. 正式批准 V6：更新 AGENTS.md、`docs/agent-contract-v6.md`、Pydantic 模型、State、适配器、JSON Schema、样例、合同测试文件名和迁移说明。

无论选择哪一个版本，都必须满足：

- 仓库只存在一个“当前生产合同版本”；
- Worker、Run、Message、Schema 和测试断言一致；
- 旧版本只作为明确标记的历史兼容资料，不再被生产导入；
- 实现人员发现合同表达不了证据装配时提交变更申请，不修改冻结文件绕过。

Prompt 建议采用单一生产来源：

```text
backend/app/agents/prompts/*.md
  -> prompt_registry 使用 importlib.resources 加载
  -> 启动时校验六个 Agent Prompt 完整
  -> 计算 prompt_version + prompt_hash
  -> 每次 Agent Run 记录版本和 hash
```

内联 `SYSTEM_PROMPT` 与 Markdown 二选一；本方案推荐使用已存在的 Markdown 目录作为生产来源，并删除或改为只引用注册器的重复内联正文。Prompt 不做成管理员按领域编辑项，专业事实继续来自当前领域证据。审核策略决议后同步清理“进入人工复核”或“自动失败”等过期互斥表述。

测试：

- 启动时发现缺失 Prompt 直接失败并指出 Agent；
- 六个 Agent 的 Run 具有不同或明确独立的 prompt hash；
- 合同常量、Schema、示例、文档和测试只指向同一版本；
- 测试文件名与实际合同版本一致；
- 生产代码不再存在未使用却声称生效的 Prompt 文件。

完成标准：开发者可以从一处确认生产合同版本、从一处确认每个 Agent 的 Prompt，运行记录能够证明实际加载的版本和哈希。

### 7.16 阶段总完成标准

- 前端主用流式接口真实调用 Tutoring Agent 并可能创建统一反馈任务；
- Feedback、AnswerRecord、KnowledgeAssessment、画像新版本和局部刷新形成可追踪证据链；
- 简答题由真实模型按结构化 rubric 辅助评分并给出评语；
- 学习路径可以按结构化完成证据推进；
- Agent Message、SSE、数据库和前端状态相互一致；
- 正式演示无法触发评测画像覆盖；
- 合同和 Prompt 各自只有一个生产事实来源；
- 上述每一项都有至少一个失败案例和一个成功案例的自动化测试。

## 8. 阶段 5：优化生成和双模型审核速度

### 8.1 目标

在不取消三类资源、来源门禁和双模型审核的前提下，减少重复检索、重复声明和不必要复审。

当前正式 50 案例基线：

| 指标 | 当前值 | 最终目标 |
|---|---:|---:|
| 端到端 P50 | `87.6s` | `<=30s` |
| 端到端 P95 | `206.8s` | `<=30s` |
| 生成节点 P50 | `59s` | 单 Agent 平均 `<=10s` |
| 审核节点 P50 | `21s` | 单 Agent 平均 `<=10s` |
| 导学分类 P50 | `23s` | 首个完整业务结果 `<=10s` |

阶段性目标可以先做到端到端 P50 `<=30s`、P95 `<=60s`，但这只算“有明显改善”，不算满足需求文档的最终 `<=30s` 验收。

### 8.2 保留现有正确设计

- 三类资源独立结构化合同；
- 三路生成并行；
- 生成只能使用检索证据；
- 双模型事实和来源审核；
- 两轮字段级局部修订；
- 未解决资源不发布；
- 学习包原子发布。

同时提供两个真实运行策略，但质量门禁相同：

| 模式 | 使用场景 | 差异 | 不允许变化 |
|---|---|---|---|
| `demo_fast` | 答辩和常规交互 | 每包 3～5 个目标、较短资源、尽可能少的动态审核批次、优先命中合规缓存 | 真实模型、真实 RAG、双审核、来源与三项质量门槛 |
| `full_quality` | 完整报告或离线交付 | 允许更长说明和更多目标，延迟预算更高 | 真实模型、真实 RAG、双审核、来源与三项质量门槛 |

模式由服务端生成策略选择，不作为领域配置，也不改变 Agent 合同字段；正式 evaluation 必须记录所用模式。任何模式都不能使用 fixture、复制主审结果充当副审或跳过未命中缓存的模型调用。

### 8.3 第一步：一次主检索

```text
Profile Agent 输出目标
  -> Retrieval Agent 一次主检索
  -> 形成共享证据池
  -> 按资源目标切片
```

- lecture 使用概念和原理证据；
- practice guide 使用操作、命令、预期结果和排错证据；
- graded quiz 使用目标知识和已批准参考题；
- 只有问题声明进入仲裁补检。

缓存键：

```text
domain_code + active_index_version + query_text + retrieval_plan
```

### 8.4 第二步：收敛生成目标

每个学习包只覆盖 3～5 个核心知识目标。

| 资源 | 建议输出 |
|---|---|
| 讲义 | 3～5 个概念、1～2 个例子 |
| 实操/任务指南 | 4～7 个步骤 |
| 分阶测试 | 每层约 2 题 |

更多薄弱知识拆成多个路径节点，不能生成超大资源包。

### 8.5 第三步：确定性预审核

模型审核前先检查：

- Pydantic/JSON Schema；
- source_ref 白名单；
- 期望知识覆盖；
- 题目层级、数量和答案；
- 实操证据能力；
- 禁止元声明；
- 难度范围；
- 代码、命令和固定输出直接证据。

结构失败直接调用定向修复，不进入主副模型语义审核。

### 8.6 第四步：原子声明和去重

把资源事实拆成单一可核验声明：

- 标题和教学动作不作为事实；
- 代码、命令、版本边界单独成声明；
- 相同事实跨资源合并；
- 每个字段仍保留自己的引用映射。

```text
claim_key = hash(normalized_claim + cited_evidence_hash)
```

### 8.7 第五步：动态批量双审核

优化前常见模式：

```text
每资源 × 主审/副审 × 多批次
```

优化后：

```text
全包唯一声明
  -> 按 token 预算动态分批
  -> 主模型批次并行
  -> 副模型相同批次独立并行
```

正常小学习包目标：

| 阶段 | 目标调用 |
|---|---:|
| 生成 | 3 次，并行 |
| 首轮审核 | 主、副各 1 个或少量动态批次 |
| 仲裁 | 只处理问题声明 |
| 修订 | 只修改问题字段 |
| 复审 | 只复审修改声明 |

主副模型使用不同模型名称，互相不可见结论。

### 8.8 第六步：仲裁和局部修订

触发仲裁：

- verdict 不一致；
- 一方通过、一方失败；
- 分数差大于 10；
- 任一方证据不足；
- 任一方发现矛盾。

```text
问题声明
  -> 重新检索
  -> 主副复审
  -> 仍 unresolved
  -> 只修订相关字段
  -> 只复审修改声明
  -> 最多两轮
```

两轮后仍未解决，整包失败。

### 8.9 第七步：审核缓存

```text
normalized_claim
+ evidence_hash
+ model_role
+ actual_model
+ review_prompt_version
+ provider_mode
```

知识、证据、模型、Prompt 或 provider mode 变化时失效。fixture 缓存不能被 live 和 evaluation 命中。

### 8.10 第八步：导学链路提速

当前导学分类 P50 为 `23s`，不能只优化三类资源生成。导学使用以下顺序：

1. 确定性检查会话、资源、领域、输入长度和可用来源；
2. 对明确快捷标签复用已保存的标签，不让模型重复识别已知字段；
3. 自然语言只调用一次 Tutoring Agent，单次结构化输出同时返回 reply、intent、action、evidence 和 decision reason；
4. 资源问答与意图分类共享同一个裁剪后的资源证据包，禁止再次做等价检索；
5. 会话历史使用增量摘要，只传最近必要轮次；
6. 流式接口发送立即可见的 `accepted/agent_status`，最终回复仍来自真实 Agent 结果；
7. 只有 Agent 决策需要复核或生成且对应门禁通过时才启动统一任务：资源错误复核校验错误标记/对话证据，画像驱动生成校验 confirmed assessment。

不得为了降低首字节时间再次直接调用 `gateway.stream_text()` 绕过 Tutoring Agent。导学性能验收同时检查业务记录完整性。

### 8.11 不允许的提速

- 取消双审核；
- 使用规则结果伪装模型审核；
- 一个模型调用伪装多个 Agent；
- 三类资源合并成一次容易截断的大调用；
- 绕过来源检查；
- 未解决资源先展示；
- 用前端假进度代替真实 Agent Run。

### 8.12 测试和观测

每次任务记录：

- 各阶段调用数；
- 输入输出 token；
- 检索、生成、审核、仲裁、修订耗时；
- cache hit；
- 唯一声明数量；
- 被去重声明数量；
- 修订字段数量；
- provider mode 和模型名。

延迟必须拆分为：

```text
queue_wait
profile
retrieval
generation
review
arbitration
revision
persist_publish
end_to_end
```

同一版本报告必须记录样本数、P50、P95、失败数、缓存命中率、模型/Prompt/知识索引版本和运行模式。正式验收不能只报告成功案例的平均值。

回归测试：

1. 三类资源仍独立；
2. 主副审核仍是不同模型；
3. 去重后字段引用不丢失；
4. 无问题包不触发仲裁；
5. 单字段问题不重写整资源；
6. fixture 不进入正式缓存；
7. 质量指标不因提速下降；
8. `demo_fast` 与 `full_quality` 都使用真实模型和相同发布门禁；
9. 流式和非流式导学的 Run、Feedback、Message 和 task 一致；
10. 50 案例报告把延迟作为验收条件，而不只是附加统计。

### 8.13 完成标准

- 同一包只有一次主检索；
- 三类生成并行；
- 结构错误在模型审核前发现；
- 审核按唯一声明动态批处理；
- 仲裁和复审只处理问题声明；
- 正式运行可证明所有 Agent 和模型调用真实；
- 50 例质量门槛保持达标；
- 阶段性达到端到端 P50 `<=30s`、P95 `<=60s` 后才能进入最终压测；
- 最终固定验收集端到端 P95 `<=30s`、单 Agent 平均 `<=10s`；
- 若质量达标但延迟未达标，本阶段状态仍为未完成，报告不得标记 competition acceptance 全通过。

## 9. 阶段 6：完成评测和第二领域证明

### 9.1 主领域正式评测

离线 `test_script` 是事实来源，至少 50 个固定案例：

| 指标 | 门槛 |
|---|---:|
| 幻觉率 | `<5%` |

| 核心覆盖 | `>=90%` |
| 端到端 P50 | `<=30s` |
| 端到端 P95 | 最终 `<=30s` |
| 单 Agent 平均 | `<=10s` |

评测固定：

- 主领域知识版本；
- Candidate manifest；
- embedding 模型；
- generation model；
- primary/secondary review model；
- Prompt version；
- provider mode；
- 评测输入和金标准。

评测 case 通过隔离 runner 创建真实测试 learner/profile/task，不再把 case marker 拼入普通 `learning_goal`。报告必须同时输出质量和延迟；失败重试、超时和排队时间均保留在原始明细中。

前端指标面板只展示离线结果，不自行计算替代。

### 9.2 画像判断评测

固定案例：

- 应更新/不应更新；
- 向上/向下；
- 资源错误但画像不变；
- 环境错误但画像不变；
- 证据冲突；
- 重复证据；
- 阈值边界；
- 跨领域证据。

建议门槛：

| 指标 | 目标 |
|---|---:|
| 更新决策准确率 | `>=90%` |
| 无证据错误更新率 | `<2%` |
| 重复证据二次消费 | 0 |
| 资源错误导致画像下降 | 0 |

### 9.3 第二领域数据规模

第二领域只用于证明无代码迁移，不与主领域同规模：

- 10～15 个真实知识点；
- 必要前置和相关关系；
- 约 10 道已审核诊断题；
- 至少 2 个差异化学习者；
- 完整来源和 Candidate 索引。

### 9.4 第二领域证明步骤

```text
管理员创建领域
  -> 上传文档
  -> 复核知识、关系和题目
  -> readiness
  -> 发布
  -> 学习者选择新领域
  -> 诊断
  -> 画像和路径
  -> 三类资源
  -> 双审核
  -> 导学反馈
```

验收：

- 全程不修改代码和 Prompt；
- 不出现主领域题目、知识和来源；
- 新领域画像使用新知识 ID；
- 三类资源只引用新领域来源；
- Agent Run、Message 和 State 真实；
- 反馈证据和画像更新属于新领域。

### 9.5 完成标准

- 主领域 50 例评测可复现并达标；
- 画像决策评测达标；
- 简答题 AI 评分、路径推进和仲裁 SSE 固定案例通过；
- 正式演示 environment override 为 false；
- 端到端和单 Agent 延迟达到最终门槛；
- 第二领域通过同一管理员流程发布；
- 完整闭环无需代码修改；
- 答辩录屏能展示真实导入和运行过程。

## 11. 数据、API 和前端改造

### 11.1 数据最小化原则

MVP 不建立完整领域、知识和资源版本体系。

新增结构只限于：

- Domain.status；
- KnowledgeItem 必需元数据；
- 一个通用导入候选表；
- AnswerRecord 的安全评分和证据元数据；
- LearningPath `path_json` 内的轻量节点状态，不新增复杂路径状态表。

其余候选内容优先使用 JSON 字段，避免为每种候选增加表。

### 11.2 核心数据一致性

所有核心对象必须能追溯领域：

```text
Domain
  -> KnowledgeDocument
  -> ImportCandidate
  -> KnowledgeItem / Relation / Question
  -> Candidate Manifest
  -> Diagnostic Session
  -> Learner Profile
  -> Generation Task
  -> Resource / Review / Feedback
```

约束：

- 关系两端同领域；
- 题目和知识同领域；
- 画像、任务和学习者目标领域一致；
- 资源和反馈继承任务领域；
- Candidate chunk metadata 与 manifest 领域一致。

### 11.3 API 统一规则

所有新增和修改接口：

- 使用 `/api/v1`；
- 返回 `schema_version`；
- 返回 `request_id`；
- 成功使用 `data`；
- 失败使用 `error`；
- 长任务使用 SSE；
- 错误信息区分阻断和可重试；
- 前后端类型同步修改。

新增业务接口必须遵守额外约束：

- tutoring 流式和非流式接口共享同一服务，不允许各自创建 Feedback；
- learning path complete 必须引用服务端可验证证据；
- evaluation case ID 只允许服务端评测 runner 使用；
- SSE 事件中的业务 ID 必须可以回查数据库；
- 简答题模型评分失败返回可重试状态，不伪装为已完成。

### 11.4 前端状态

所有核心页面具备：

- loading；
- empty；
- failure；
- retry；
- 当前领域提示；
- 后端真实状态。

导入页面不能只显示“处理中”：

```text
parsing
extracting
validating
awaiting_review
indexing
smoke_testing
ready_to_publish
published
failed
```

错误至少定位到文件、候选 ID、关系或题目字段。

导学、诊断和报告页还必须显示：

- 导学：intent、recommended action、是否更新画像、decision reason、真实 task ID；
- 简答题：AI 分项得分、缺失点、评语和不确定状态；
- 学习路径：locked/current/completed/skipped、完成条件和证据；
- 仲裁：主副结论、重新检索、复审和最终状态；
- 正式环境不展示或接受 evaluation marker。

### 11.5 Agent 可视化

前端展示真实节点状态：

```text
prepare_task
interpret_feedback（仅反馈）
analyze_profile
retrieve_knowledge
generate_resource
review_resource
finalize_task
```

状态来自真实 Agent Run 和任务事件，不能使用固定计时器模拟。

Agent Message 只展示真实节点交接审计；页面说明 LangGraph State 是实际传递机制。审核分歧节点的高亮条件来自 ReviewReport 的 `arbitration.required`，不能由前端根据固定步骤猜测。

### 12.5 真实性检查

正式演示和 evaluation 必须验证：

- provider mode 不是 fixture；
- 主副模型名不同；
- 每个真实 Agent 有 Run；

- Candidate RAG 使用真实 active manifest；
- 来源可定位；
- 前端状态来自后端事件；

- 普通演示环境 `evaluation_overrides_enabled=false`；
- 简答题至少有一次真实评分模型调用；
- 路径完成有服务端结构化证据；
- 仲裁 SSE 能回查到 ReviewReport；
- 合同版本和 Prompt hash 与实际运行记录一致；
- 延迟不被排队等待、失败重试或 fixture 样例从报告中剔除。

里程碑编号按原主题保留，实际执行顺序为 `M0 -> M4A -> M4B -> M1 -> M2 -> M3 -> M4C -> M5 -> M6`。

### M0：基线可重复

产物：

- 主领域基线清单；
- 固定演示用户和任务；
- 回归测试结果；
- 质量、延迟和反馈更新计数基线；
- 正式演示 evaluation override 关闭证明；
- V5/V6 合同维护决议记录。

完成定义：后续每个阶段都能用同一案例判断是否回归。

- 候选表和迁移；
- parser/extractor/validator/publisher；
- 管理员候选复核；
- Candidate 索引和发布。

完成定义：上传一份多章节文档后，能批准多个知识点、关系和题目，并用于主领域检索。

### M2：领域运行时通用

完成定义：测试领域能创建诊断和画像，代码没有主领域 fallback。

## 15. 附录：统一标准和算法规则

### 15.1 平台固定与领域变化

| 平台固定 | 领域数据变化 |
|---|---|
| 五维画像 | 知识点能力权重 |
| 1～5 难度尺度 | 具体知识和题目的难度标定 |
| 学习路径算法 | 知识关系 |
| 三类资源合同 | 专业内容、示例和任务 |
| 多 Agent 工作流 | 来源文档和题库 |
| 双审核和仲裁 | 领域事实证据 |
| 反馈证据门禁 | 当前领域知识 ID |
| 三项质量门槛 | 领域评测案例 |

### 15.2 统一难度

| 等级 | 含义 |
|---:|---|
| 1 | 识记和识别 |
| 2 | 解释和直接应用 |
| 3 | 常见情境组合应用 |
| 4 | 异常分析和复杂约束 |
| 5 | 综合设计和迁移权衡 |

### 15.3 个性化如何产生

两个学习者都不会同一知识点时，核心专业证据相同或高度重合；个性化来自：

- 是否补检前置知识；
- 讲解顺序；
- 理论深度；
- 步骤拆解粒度；
- 示例类型；
- 错误提示；
- 题目难度；
- 单次目标数量。

因此是“知识同源、教学表达和训练因人而异”。

### 15.4 五维画像

- 理论；
- 实践；
- 问题解决；
- 知识广度；
- 学习速度。

知识广度需要类别覆盖证据；学习速度至少需要多个带时间记录的任务。二者不能由一次答题或对话猜测。

### 15.5 审核门槛

- 事实和来源由主副模型独立审核；
- 分数差大于 10 或 verdict 不一致触发仲裁；
- unresolved 资源不展示；
- 最多两轮局部修订；
- 幻觉率 `<5%`；
- 难度适配 `>=85%`；
- 核心覆盖 `>=90%`。

### 15.6 最终答辩表述

改造完成前：

> 当前主领域已完成真实 Candidate RAG 和多 Agent 生成审核闭环，但诊断、画像和导学仍有主领域硬编码，不能宣称只换知识库即可完整迁移。

改造完成后：

> 系统采用通用个性化教学引擎和标准化领域知识数据分离架构。管理员上传文档后，系统生成知识点、关系、题库、难度和能力元数据候选，经复核和索引发布后，同一套多 Agent 流程无需修改代码即可运行新领域。

## 最终执行摘要

开发团队按以下顺序执行，不并行跨越依赖：

```text
M0 基线
  -> M4A 流式导学、反馈任务和证据装配
  -> M4B 简答题 AI 评分和学习路径推进
  -> M1 真实知识导入
  -> M2 领域去硬编码
  -> M3 管理员无代码闭环
  -> M4C 可观测性、评测隔离和合同/Prompt 治理
  -> M5 生成审核提速
  -> M6 评测和迁移证明
```

真正的第一项优化是修复当前流式导学的真实性断链；领域建设的第一项功能优化是把实验上传变成可复核、可校验、可发布的结构化知识导入。二者分别解决“现有演示闭环真实”和“新领域数据可用”，不能互相替代。
